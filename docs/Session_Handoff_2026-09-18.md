# 2026-09-18 현재 상태와 다음 목표

기록 시각: 2026-09-18 14:11 KST. 오늘 검증 결과와 사용자가 정한 후속 작업 방향을 기록한다.

## 결정

**현재 localization을 후속 개발의 기준 상태로 채택한다. 추가 성능 개선보다 구현과 실행 절차를 먼저 정리하고, 그 다음 RViz 2D Goal Pose 기반 자율주행을 완성·검증한다.**

사용자는 128MiB 커널 설정의 효과가 명확하고, 현재 localization이 우수하게 동작하므로 남은 작은 흔들림이나 수신 오류를 더 최적화하는 것보다 다음 단계로 진행하는 것이 적절하다고 판단했다. 이 결정은 앞선 진단 보고서의 “UDP/DDS 추가 측정 우선” 제안보다 우선한다. 관측된 문제를 없었던 것으로 처리하는 것이 아니라 후속 개선 항목으로 남기는 결정이다.

## 오늘 확인한 기준 상태

- 노트북의 `net.ipv4.ipfrag_high_thresh`를 4MiB에서 **128MiB (`134217728`)**로 임시 변경했다. AMCL·FAST-LIVO2 파라미터는 이번 시험에서 변경하지 않았다.
- `nav_bringup.launch.py` 기동 → RViz `2D Pose Estimate`로 초기 위치 지정 및 지도·scan 정합 확인 → 별도 터미널에서 `mid360_bringup perception.launch.py` 실행 순서를 검증했다.
- Nav2와 perception을 함께 실행한 상태에서 사용자가 좌우 제자리 회전을 수행했다. 사용자는 정합 유지를 확인했고, 기록에서 기존의 큰 TF 발산이나 FAST 자동 종료는 재현되지 않았다.
- FAST `odom → base_link` z 최대−최소 범위는 정지 전 8.1mm, 회전 포함 구간 17.0mm, 정지 재확인 6.4mm였다. 지속적인 큰 높이 발산은 관측되지 않았다. 현재 개발을 막는 문제로 취급하지 않는다.
- 회전 뒤 약 0.5m 이동은 사용자의 실제 수동 이동이었다. 이를 localization 드리프트로 해석하지 않는다.
- YOLO 검출과 3D 검출·추적 메시지가 실제로 수신됐다. 회전 포함 구간에서 YOLO 약 11.1Hz, 3D 검출·추적 약 10.1Hz였다.
- 실제 FAST 노드 이름은 `/laserMapping`, 로그 이름은 `fast_livo`이다. AMCL은 `nav2_amcl::OmniMotionModel`, alpha1~5=0.2를 사용했다.
- **자동주행은 아직 실기 검증하지 않았다.** 오늘 움직임은 수동 조작이며, `enable_motion=false` 및 실제 `forward_cmd_vel=false`를 확인했다.

상세 근거: [오늘의 검증 보고서 및 그래프](validation/2026-09-18/z_axis_test_1351/REPORT.md), [9월 17일 커널 한도 비교 시험](Staged_Network_Pilot_2026-09-17.md).

128MiB 적용의 효과는 기존 비교 시험과 사용자 관찰, 오늘 검증이 함께 뒷받침한다. 다만 localization의 절대 정확도를 ground truth로 측정한 결과는 아니며, 네트워크 오류가 모두 사라졌다는 의미도 아니다.

## 1단계 — 구현과 실행 절차 정리

현재 잘 동작하는 설정과 실행 순서를 보존하면서 다음 항목을 정리한다. 아래는 작업 목표이며 아직 구현 완료 상태가 아니다.

1. **진입점과 역할 정리:** 실제 launch·노드·스크립트를 기준으로 권장 진입점을 `nav_bringup.launch.py`로 정리하고, 과거 수동 절차 및 다른 bringup 경로와의 관계를 명확히 한다. FAST는 현재 staged launch에 포함되며 perception은 별도 터미널에서 실행한다.
2. **커널 설정 절차 정리:** 128MiB를 기준 실행 조건으로 문서화하고, 현재 값 확인·적용 여부 안내·종료 및 복원 절차를 재사용 가능하게 만든다. 현재는 임시 설정이며 `/etc/sysctl.d` 등을 통한 영구 적용은 하지 않았다. 영구 적용 방식은 이 정리 단계에서 다룰 구현 항목이다.
3. **기동·준비·종료 상태 정리:** 센서 입력 → FAST odometry → localization 준비 → 수동 초기 위치 → perception의 단계를 일관되게 안내한다. 실패·중단 시 후속 프로세스 기동 방지, 중복 실행 방지, 종료 순서를 검토한다.
4. **perception 준비 판정 정리:** 오늘 연결 검사는 YOLO 로딩보다 먼저 타임아웃했지만 이후 검출은 정상 동작했다. 로딩 중과 실제 준비 실패를 구분하도록 상태 표시와 판정 시점을 검토한다.
5. **설정과 기록 정리:** 실제 노드 이름, TF 소유권, 센서 장착 변환, 토픽 경로, perception 프로파일 생성 방식을 정리한다. 필요한 진단 로그를 프로젝트 내에 남겨 `/tmp` 소실이나 세션 중단 뒤에도 상태를 복원할 수 있게 한다.

완료 기준은 같은 설정으로 권장 순서를 재현할 수 있고, 준비 여부·실패 원인·초기 위치 설정 시점·종료 방법이 명확한 것이다. README의 오래된 현재 상태 설명과 실제 구현 사이의 차이도 이 단계에서 정리한다.

## 2단계 — 2D Goal Pose 기반 자율주행

1단계 후 **RViz에서 목표 위치·방향을 지정하면 Jackal이 경로를 따라 이동하고 목표에 도달해 정지하는 흐름**을 완성한다.

- `2D Pose Estimate`는 localization 초기화, `2D Goal Pose`는 이동 목표 지정으로 구분한다.
- 현재 RViz에는 `/goal_pose`로 발행하는 `SetGoal` 도구가 있고, navigation launch에는 planner/controller/BT navigator가 이미 있다. 전부 새로 구현한다고 가정하지 않고 기존 목표 수신 경로와 실제 동작을 먼저 확인한다.
- 목표 수신 → 경로 계획 → 제어 → 속도 평활화 → 기존 collision monitor/safety guard → 로봇 명령 전달 경로를 점검하고 누락된 연결을 보완한다.
- 현재 꺼져 있는 motion 설정과 로봇 측 전달 설정의 관계를 정리하고, 기동 시 localization 준비와 실제 주행 가능 상태를 구분한다.
- 짧은 목표 이동부터 시작해 목표 방향 정렬, 도착 정지, 목표 취소·변경, 기존 정지 동작을 실기로 확인한다.

완료 기준은 목표 전달 또는 경로 표시만이 아니라, 실제 Jackal의 목표 도달·정지와 결과 기록이다. 오늘은 이 단계의 목표를 기록했으며 목표 전송이나 자율주행 활성화는 수행하지 않았다.

## 지금은 보류하는 항목

- 추가 AMCL/FAST 파라미터 튜닝, z 강제 평면화, 작은 z 진동의 추가 최적화.
- UDP/DDS 수신 성능의 추가 최적화. 오늘 최대 약 0.35초 odometry 수신 간격과 커널 수신 오류는 남아 있었으나 이번 개발 단계의 선행 과제로 삼지 않는다. 이후 기동이나 자율주행을 실제로 방해하면 해당 증거를 기준으로 다시 다룬다.
- CPU/RAM 사용량에 따른 보호 정책 추가. 사용자의 기존 요청대로 현재 범위에 넣지 않는다.

## 세션 재개 시 참고

아래는 **검증 종료 직후 마지막으로 확인한 상태**이며, 다음 세션의 현재 상태를 보장하지 않는다.

- Nav2/FAST 및 별도 perception은 실행 중으로 남겨 두었다. 기록기 2개는 정상 종료했다. 자동 속도 전달은 비활성 상태였다.
- 128MiB는 사용자 sudo 터미널의 `/tmp/nav_z_20260918_1351/hold_ipfrag.sh`가 유지했다. 시험 스택 종료 후 `restore.request`를 생성하면 기존 4MiB로 복원하는 방식이었다.
- 재접속 시 기존 프로세스와 **ROS가 실행되는 실제 호스트 네트워크의** 커널 값을 먼저 확인한다. 격리된 도구 환경의 `/proc/sys` 값은 호스트 값과 다를 수 있다. `/tmp` 스크립트나 이전 세션 ID의 존재를 가정하지 않는다.
- [검증 산출물 폴더](validation/2026-09-18/z_axis_test_1351/)에 실제 파라미터, 시계열, 사용자 확인 이벤트, 분석 결과 및 `runtime_state.json`을 저장했다.
